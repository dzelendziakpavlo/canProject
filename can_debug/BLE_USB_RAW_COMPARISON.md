# Порівняння Android raw BLE та USB Serial

Дата перевірки: 2026-11-09.

**Підтверджено: суперечливі поля та невалідний JSON уже присутні в
Android platform-channel log до Dart reassembly, frame mapper, tracker,
SQLite та експорту.** USB-запис відповідного потоку послідовний.
Точне місце всередині BLE-шляху — ESP32 TX, Bluetooth/GATT або Android
native bridge — цими файлами ще не визначене.

## Джерела та зіставність

Користувач надав `build/ble_raw.log` і `capture.csv/capture.jsonl/manifest.json`
з каталогу експерименту `capture_1794235204090919_48681363`.
Попри назву «PC simulation» у повідомленні, manifest визначає джерело
як `transport=usbSerial`, `COM5`, `460800`, `source=USB Serial — COM5 @ 460800`.
1823 повні BLE-об'єкти збігаються з USB за всіма JSON-полями, включно з
`seq`, receiver `ts`, ID та data. Файли містять зіставний потік RECEIVER;
висновок не спирається лише на час різних пристроїв або назву джерела.

USB записаний 14:40:04.088919Z–14:41:04.589632Z. BLE log показує час
16:40:06.689–16:41:00.844 для повних FF11 callbacks. Годинники пристроїв
не використовувалися для вимірювання latency. Перевірялися wire-поля;
межі записів відрізняються, тому порівнювався також спільний діапазон seq.

| Показник | USB | Android raw log |
|---|---:|---:|
| CAN frames / валідні повні FF11 JSON | 2172 | 1825 |
| Діапазон seq | 15487–17658 | 15525–17478 |
| Унікальних seq | 2172 | 1823 |
| Повторних входжень seq | 0 | 2 |
| Відсутніх номерів у власному діапазоні | 0 | 131 |
| Повних, але невалідних FF11 byte lists | 0 | 1 |
| Stats | 61 повний JSON | 51 запис із обрізаним друком byte list |

## USB-запис узгоджений

- JSONL і CSV містять по 2233 записи: 2172 frames та 61 stats.
- `rawJson` і hostReceivedAt збігаються між CSV та JSONL для кожного запису;
  wire-поля та нормалізовані поля JSONL також узгоджені.
- Seq 15487–17658 послідовні без повторів та пропусків.
- Manifest: `acceptedRecords=writtenRecords=2233`, `unrecordedRecords=0`,
  `serialParseErrors=serialErrors=readErrors=sequenceGaps=0`, `failure=null`.
- У всіх USB stats лічильники transport drops, TEC/REC/missed/buserr/overrun
  дорівнюють нулю. `bledrop` відображає firmware queue drops за схемою
  прошивки, а не гарантує доставку кожного BLE notification до Android.

Після первісного порівняння користувач уточнив, що експеримент виконувався
на 460800 бод із SEND_MODE 1, та оновив файл RECEIVER у репозиторії.
Повторне порівняння з резервною копією підтвердило: єдина зміна RECEIVER
від попереднього аудиту — `SERIAL_BAUD: 115200 → 460800`.
Тепер UART узгоджений із manifest. `CAN_SERIAL_JSON=1` вибирає JSON_STREAM;
у `sender_can.ino` задано `SEND_MODE=1`. Це два різні перемикачі.
Код черг, серіалізації та BLE notify залишився тим самим.

SEND_MODE 1 задає CAN ID/data/інтервали SENDER, але не формує JSON або seq.
Seq присвоює RECEIVER після приймання CAN. Зміна UART baud також не змінює
BLE JSON-поля. Ці налаштування пояснюють конфігурацію експерименту,
але не підміну seq чи змішування data у BLE raw.

Додаткова перевірка даних режиму 1: SENDER формує
`data[1] = (data[0] * 3) & 255`, байти 2–7 залишаються нульовими.
Усі 2172 USB-кадри відповідають цьому правилу. BLE-кадр у рядку 1229
містить `[77,189,0,0,0,0,0,0]`, хоча для 77 другий байт має бути **231**.
Це додатково підтверджує суперечливість саме BLE-представлення;
джерело всередині BLE-шляху цим правилом ще не локалізоване.

SHA-256 оновленого RECEIVER:
`b785b9500b35354cffd0c439ac15debaace66787bc6e3f5cec6e37a23c7c2ddc`.
Результати повторної перевірки: `build/validation/ble_usb_compare/receiver_recheck.json`.
Перед оновленням звіту поточні 42 змінені/нові файли та Git-стан збережено
в `../.work_backups/receiver_recheck_before_20261109_165714.zip`.
Прошивку під час перевірки не редагували й не завантажували на ESP32.

## Три конкретні аномалії до reassembly

Номери рядків нижче — у вихідному `build/ble_raw.log`.
Усі три byte lists повністю закриті `]}` у тексті log record; обрізання
друку FF12 до цих прикладів не стосується.

### 1. Рядок 1031, 16:40:34.514

Android отримує:

```json
{"t":"f","id":216,"dlc":8,"data":[36,108,0,0,0,0,0,0],"ts":459076,"seq":16478}
```

USB має цей самий ID/data/ts під **seq=16480**. Справжній USB seq=16478:

```json
{"t":"f","id":200,"dlc":8,"data":[71,213,0,0,0,0,0,0],"ts":459075,"seq":16478}
```

Правильний seq=16478 вже був у BLE у рядку 1029. Отже, це друге входження
номера з іншим вмістом, а не повтор незміненого кадру. Декодер приймає JSON
як структурно валідний; його поля вже суперечливі у вхідних байтах.

### 2. Рядок 1229, 16:40:38.650

Android отримує:

```json
{"t":"f","id":416,"dlc":8,"data":[77,189,0,0,0,0,0,0],"ts":464475,"seq":16671}
```

USB seq=16671 — ID 208, data `[63,189,0,0,0,0,0,0]`, ts=464475.
USB seq=16673 — ID 416, data `[77,231,0,0,0,0,0,0]`, ts=464476.
BLE-об'єкт не збігається цілком із жодним USB-кадром за ID/data/ts.
Він містить значення з сусідніх повідомлень; це ознака змішаного вмісту,
але ще не доказ конкретного механізму пошкодження.

Правильний BLE seq=16671 є в рядку 1227. Друге входження відрізняється
ID і data ще до публікації події `onValueReceived` у Dart-плагіні.

### 3. Рядок 1406, 16:40:43.187

Повністю надрукований byte list декодується в невалідний текст:

```text
{"t":"f","id":208,"dlc":8,"data":[87,5,0,0,0,0,0,0],"ts":469275,"seq"":16843
```

Тут зайві лапки біля seq і немає закривальної `}`. USB має правильне
повідомлення з тими самими ID/data/ts, але `"seq":16845}`.
Поточний BLE decoder залишає цей partial і при наступному новому root
відкидає його як incomplete; валідний кадр із нього не створюється.

## Чому це звужує причину

У встановленому `flutter_blue_plus_android 7.0.4`,
`FlutterBluePlusAndroid._methodCallHandler`, verbose-друк
`call.arguments.toString()` відбувається **перед** обробкою
`OnCharacteristicReceived` та додаванням у controller. Наш
`BleCanSource._onFrameBytes` і `BleMessageDecoder.add` ще не викликалися
для цієї події. Відповідно, reassembler/аналізатор/SQLite/експорт не можуть
бути джерелом уже надрукованих суперечливих байтів цих callbacks.

Далі до джерела залишаються: фактична прошивка й BLE output ESP32,
Bluetooth/GATT-стек та Android native bridge до MethodChannel. Звичайний
USB-запис підтверджує правильні USB-байти, але не показує, які байти
ESP32 передав саме в BLE notify.

У native-плагіні `onCharacteristicReceived` передає byte[] у response і
відкладає MethodChannel-виклик на UI thread. Це місце варто перевірити
незалежним snapshot/digest на вході callback та перед encode; надані
логи **не доводять**, що саме цей буфер змінюється. Фікс навмання не внесено.

## Межі raw-логу

Знайдено 1877 записів OnCharacteristicReceived: 1826 FF11 та 51 FF12.
Усі 51 FF12 друкуються обрізаними: logcat-рядок має 1066 символів разом
із 42-символьним префіксом, тіло обмежене 1024 символами. Закінчення
byte list не потрапило у файл. Це не можна називати 51 помилкою JSON
на транспорті або в застосунку. Видимі повні поля uptime/rx/TEC/REC/missed/
buserr у цих prefixes збігаються з відповідними USB snapshots.

Отже, запропонований verbose-спосіб достатній для наведених FF11-доказів,
але не зберігає повністю довгі FF12. Для наступного виміру потрібен
окремий потоковий журнал byte snapshots з довжиною, номером callback і
monotonic time, без залежності від друку довгої строки logcat.

У діапазоні 15525–17478 USB містить 1954 кадри; у валідному BLE-логу
немає 131 унікального номера. Це **відсутність у зібраному логу**, а не
доведена кількість втрат BLE: друк/logcat також можуть пропускати записи.
Два номери підмінено у валідних JSON, ще одному відповідає malformed
callback; решта причин не встановлена. Повний Android JSON цієї ж сесії
дозволить відрізнити втрати журналювання від відсутніх прийнятих кадрів.

MTU успішно узгоджено як 247. У логах є одне успішне підключення й немає
disconnect-події до кінця файлу. Повного завершення сесії цей лог не містить.

## Перевірки й артефакти

Поточний Dart decoder програв 1826 повних byte lists FF11 без зміни
вхідних байтів: accepted=1825, incomplete=1, rejected=0. Tracker отримав
gaps=131, duplicates=2, outOfOrder=2, resets=0. Дві суперечливі frame models
мають ті ж самі значення, що їхні raw inputs. Replay-тест пройшов.
Це перевірка наданих байтів, а не новий фізичний експеримент.

Артефакти в ігнорованому `build/validation/ble_usb_compare/`:

- `analyze.py` — аналіз наданих чотирьох файлів;
- `analysis.json` — усі результати, відмінності й хеші;
- `decoded_notifications.jsonl`, `raw_notifications.json` — витягнуті
  об'єкти й повні byte lists, включно з malformed FF11;
- `replay_test.dart`, `replay_test.log` — відтворення поточним decoder.

Вихідні файли не змінено; SHA-256 перевірено повторно після читання:

| capture.jsonl | 16f09ca7ce59867c23bc07287745298f79bb7223f4f791827d693fe319a63a51 |

Код застосунку й firmware в цьому порівнянні не змінювались. Перед
оновленням документації збережено 41 змінений/новий файл та Git-стан у
`../.work_backups/ble_raw_comparison_before_20261109_164737.zip`.
Попередній користувацький рядок `LogLevel.verbose` збережено.

Наступний точний експеримент: зіставити bytes/digest безпосередньо перед
ESP32 notify з native callback Android, а потім з MethodChannel.
Альтернатива для розділення TX та Android — цільовий HCI trace цього
пристрою. До цього оновлення SQLite/UI або переписування seq не мають
доказової підстави й можуть приховати симптоми.

## Підготовлений наступний етап

За окремим погодженням реалізовано локальний Android native snapshot і
опційний файловий raw trace з обмеженою чергою та mutation probe.
Програмні перевірки пройшли; фізичне усунення проблеми ще не підтверджене.
Команди збірки, start/stop/pull/compare та критерії оцінки:
[ANDROID_BLE_NATIVE_EXPERIMENT.md](ANDROID_BLE_NATIVE_EXPERIMENT.md).
ESP32/HCI tracing у цьому етапі не виконується.

### Контрольний запис після native patch

Отримано й незалежно перевірено `build/ble_native_comparison.json` разом
із його вихідними JSONL. Native journal повний: 9049 callbacks, dropped/write
errors=0. Усі оригінали порівняні; змін між entry snapshot і UI dispatch
немає. Аномалії залишилися: 41 невалідний JSON callback (39 FF11, 2 FF12),
15 відмінностей CAN JSON від USB та 4 відмінності rx у stats.
USB-потік послідовний. Патч не усунув проблему в цьому записі; гіпотеза
після-callback мутації byte[] не підтвердилася в дослідженому вікні.
Деталі й межі висновку — в розділі «Результат контрольного запису користувача»
інструкції вище. Нові firmware/native/HCI зміни після цього результату
не виконувались; наступний крок вирішується окремо.
