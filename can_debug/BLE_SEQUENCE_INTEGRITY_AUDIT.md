# BLE Sequence Integrity — аудит і виправлення

Дата: 2026-11-09.

Виправлено підтверджені помилки **обліку послідовності**. Після первісного
аудиту користувач надав сам експорт `Schema 2`; його повністю перевірено,
і всі старі лічильники точно відтворено з кадрів. Першопричину суперечливих
повідомлень з однаковими `seq` поки не встановлено. Детальний розбір
реального файлу наведений у розділі 7. Фізичного тесту в цьому аудиті не було.

## 1. Підтверджені причини

Попередній `BleSequenceTracker.accept` у `lib/domain/source/ble_message_decoder.dart`:

```dart
if (delta >= 0x80000000) {
  if (ts != null && _lastTs != null && ts < _lastTs!) {
    resets++;
  } else {
    outOfOrder++;
    return;
  }
}
// Після хибного reset:
_last = seq;
_lastTs = ts;
```

1. **Хибний reset.** Старий кадр має менші `seq` і час його захоплення `ts`.
   Така пара не доводить перезавантаження. FF12 `uptime` взагалі не
   використовувався лічильником послідовності.
2. **Повторне нарахування пропусків.** Після такого reset базовий `seq`
   зсувався назад. Приклад: отримати всі `1037…1076`, потім повтор `1037`,
   потім `1077`. Старий код нараховував reset і 39 пропусків, хоча пропущених
   номерів немає. Новий тест перевіряє `gaps=0`, `duplicates=1`,
   `outOfOrder=1`, `resets=0`.
3. **Недооблік повторів.** `duplicates` збільшувався лише при `seq == _last`,
   а не при повторі будь-якого вже отриманого номера в поточній епосі.
   Тому повтор старішого номера міг стати reset або out-of-order.

До виправлення дві регресійні перевірки завершилися помилками:
`older sequence and capture timestamp do not prove receiver reset`
і `nonadjacent replay is counted without moving high water backwards`.
Після виправлення вони проходять.

### Чому 138 не дорівнює 27

`6848 - 1003 + 1 = 5846`; `5846 - 5819 = 27` — кількість **відсутніх
унікальних номерів** у зазначеному діапазоні, якщо в ньому одна епоха receiver.
`5839 - 5819 = 20` — повторні входження номерів у цьому масиві.

Старі `sequenceGaps=138` — сума стрибків від змінюваної бази; це не
потужність множини відсутніх номерів. До неї могли входити повторні стрибки
після хибних reset. Навіть правильний облік початкових стрибків не зменшує
їх при запізнілому надходженні кадрів: `100,103,101,102` має 2 початкові
пропуски, але 0 остаточно відсутніх номерів.

Після отримання експорту точний розклад підтверджено:
**138 = 27 відсутніх номерів + 111 повторно нарахованих позицій** після
десяти хибних класифікацій reset. Усі 160 snapshots мають зростаючі
`uptime/rx`, навколо кожного з цих переходів телеметрія продовжується.
Старі `duplicateSequences=3` відображають лише повтор поточного базового
номера, тоді як повторних входжень у масиві двадцять. Старі метадані
не переписуються; точні переходи наведено в розділі 7.

## 3. Семантика нових лічильників

Нові завершені BLE-сесії містять `sequenceTrackingVersion=2` та явні поля
`sequenceGapSemantics`, `duplicateSequenceScope`, `receiverResetEvidence`.
Сесії без версії залишаються з історичною семантикою.

| Поле | Семантика версії 2 |
|---|---|
| `sequenceGaps` | Сумарна кількість пропущених позицій при просуванні найбільшого отриманого `seq` вперед. Не зменшується при запізнілому заповненні. Не дорівнює остаточним втратам BLE або CAN. |
| `duplicateSequences` | Кожне повторне входження вже побаченої позиції в поточній визначеній епосі receiver, включно з не сусідніми повторами. Це повтор номера, не гарантія побайтової тотожності повідомлення. |
| `outOfOrder` | Кожен кадр позаду найбільшої отриманої позиції. Старий повтор може збільшити і цей лічильник, і `duplicateSequences`. Сума цих полів не є кількістю різних пошкоджених кадрів. |
| `receiverResets` | Телеметрично підтверджені зміни бази: спільний відкат FF12 `uptime` та `rx`, потім ще один snapshot із зростанням uptime і незменшенням rx, обидва нижче попередньої бази. Один старий snapshot або старі FF11 `seq/ts` недостатні. |
| `missingSequence` | Прийняті валідні повідомлення без optional `seq`. |

Для seq і телеметрії використовується uint32 modular arithmetic: кроки
мають бути менші за `2^31`. Звичайний wrap не вважається reboot. При
підтвердженій новій епосі очищаються лише база та інтервали побачених номерів;
накопичені лічильники зберігаються. Звичайний reconnect не обнуляє tracker.

Повтори пам'ятаються через впорядковані неперервні інтервали номерів.
Пам'ять залежить від кількості розірваних інтервалів; суцільний потік займає
один інтервал, без зберігання копій кадрів у tracker.

Консервативні обмеження reset: без FF12 uptime reset не підтверджується;
відсутні snapshots, швидке повернення лічильників вище старої бази або
неоднозначність uint32 можуть його приховати. Кадри до підтвердження
залишаються спостереженнями out-of-order/повторів відносно чинної бази;
вже нараховані спостереження не коригуються заднім числом. Протокол без
boot ID не дозволяє відрізнити reboot від відтворення цілого старого сегмента
телеметрії з абсолютною впевненістю.

Незмінені decoder-лічильники: `rejectedMessages` рахує завершені невалідні
об'єкти/переповнення, `incompleteMessages` — відкинуті partial objects,
`discardedBytes` — байти поза об'єктами. Останнє поле не включає всі байти
очищених partial buffers і не є повною оцінкою втрат на транспорті.

## 4. Достовірність кадрів і залишкові невідомі

Автоматично перевірені допустимі ID/DLC/payload/RTR/extended/seq/ts,
відповідність `rawWire` нормалізованим полям, незалежність data між кадрами
та повний roundtrip через SQLite й експорт. Після отримання реального файлу
перевірено також **усі його 5839 кадрів**: порушень цих структурних правил
і розбіжностей між `rawWire` та моделлю немає. Це не виключає семантичних
суперечностей між різними повідомленнями з тим самим `seq` (розділ 7).

Повторний notification із повним валідним JSON зберігається повторно:
це необхідно для чесної фіксації отриманого потоку. Повтор prefix-фрагмента
`{"t":…` відкидає попередній partial; невалідні з'єднання фрагментів
відхиляються. Але повтор цифрового фрагмента `1` усередині `data` може
дати валідний байт `11`. Тест відтворює цю неоднозначність: `rawWire`
відповідає зібраному JSON, але не доводить відповідність оригіналу ESP32.
Автоматично видаляти схожі фрагменти небезпечно — коректні однакові фрагменти
також можливі. Змін до reassembler або firmware за цим припущенням немає.

`crcSource=application_xor_placeholder_not_wire_crc` залишається маркером
прикладного XOR; він не підтверджує достовірність CAN wire CRC.

Для наступного експерименту мінімально потрібні: повний JSON, фактична
версія firmware, negotiated MTU, часові мітки disconnect/reconnect.
Якщо повтори збережуться — тимчасовий потоковий журнал **до reassembly**:
порядковий номер callback, monotonic host time, FF11/FF12, довжина й точні
байти notification. Порівняння з одночасним USB JSONL допоможе звузити
ділянку виникнення повторів. Сам USB-журнал не доводить доставку GATT;
за потреби наступний рівень — трасування `seq/length` біля firmware notify.
Таку додаткову інструментацію в цьому виправленні не впроваджено.

## 6. Ручна перевірка Android + ESP32

1. Оновити APK поверх наявного застосунку, не очищаючи дані. Перевірити
   доступність старих сесій. Firmware для цього тесту не змінювати.
2. Підключити RECEIVER через BLE, записати звичайний потік 1–2 хвилини,
   натиснути Stop, дочекатися збереження й експортувати повну сесію.
3. Перевірити `sequenceTrackingVersion=2`, `receivedFrames == committedFrames
   == frames.length`, `pendingRecords=0`, `storageError=null`. Порівнювати
   послідовність `seq` у первісному порядку, без попереднього сортування.
   Окремо обчислити унікальні/відсутні номери в кожній епосі; не вимагати
   їх рівності gross `sequenceGaps`.
4. Під час окремого запису розірвати лише BLE та відновити його без reboot
   RECEIVER. `uptime/rx` мають продовжуватися, `receiverResets` не зростати.
   Пропуски в період відключення очікувані; всі прийняті кадри мають лишитися.
5. Під час ще одного запису перезапустити RECEIVER, дочекатися reconnect
   та щонайменше двох нових FF12 snapshots. Зіставити відкат `uptime/rx`
   зі збільшенням `receiverResets`; попередні лічильники не повинні зникнути.
6. Якщо є аномалії — зберегти JSON разом із source-state events і за
   можливості паралельним USB JSONL. Не видаляти повтори для «вирівнювання»
   даних. Передавати лише файли цього експерименту.

### Перевірка reboot, reconnect і TWAI

Усі 160 FF12 snapshots мають `state=RUNNING`, `uptime` зростає від
38 529 до 199 550 мс, `rx` від 1044 до 6840. Відкатів або повторів uptime
немає. У snapshots безпосередньо до/після кожного з десяти «reset»
обидва значення продовжують зростати. Перезавантажень ці спостереження
не підтверджують; новий tracker їх не зараховує.

Source-state події: `connecting → connected → streaming → idle`.
Disconnect/reconnecting відсутні; `reconnectCount=0`. Аномалії не
супроводжуються зареєстрованим перепідключенням BLE.

В усіх snapshots `txe/rxe/missed/buserr/arb/txfail/ovr=0`.
Це відсутність зафіксованих помилок цих TWAI-лічильників, а не доказ
цілісності прикладних BLE-повідомлень.

### Важливе уточнення: повтор seq не означає повтор цілого кадру

Лише `seq=1371, 3952, 4283` повторюються з однаковими полями `rawWire`.
Інші **17 пар мають різний ID, data або ts**. Наприклад:

- `seq=1037`: перший ID 192, повторний ID 208; решта полів однакова.
- `seq=3343`: перший ID 192, data `[161,227,…]`; повторний ID 200,
  data `[163,227,…]`, той самий ts 102371.
- `seq=3376`: спочатку ID 216, ts 103172; потім ID 192, ts 103271,
  також інші data.
- `seq=3763`: перший ID 688, повторний ID 200; решта полів однакова.

Отже, проста гіпотеза «повторно доставлено незмінний старий notification»
не пояснює всі аномалії. Є суперечливі об'єкти з однаковим sequence number.
Можливе змішування/заміна частин повідомлення, але сам експорт не дозволяє
визначити, де це сталося: у фактичній збірці firmware, GATT/native-шляху
або reassembly. `rawWire` тут — вже декодований JSON-об'єкт; первісних
байтів та меж notifications файл не містить. За цим спостереженням нових
виправлень firmware/decoder не внесено без відтворення причини.

Тому **27 — кількість відсутніх номерів**, а не доведена кількість утрачених
фізичних CAN-кадрів. Частина повідомлень із хибним/повторним seq може нести
інші дані. Рівність `receivedFrames=committedFrames=5839`, порожня черга й
`storageError=null` підтверджують узгодженість збережених прийнятих записів,
але не повноту чи цілісність передачі від ESP32.

### Додаткова перевірка фактичним Dart-кодом

Один додатковий replay-тест реального файлу пройшов:

- Усі 5839 збережених rawWire об'єктів повторно декодовано поточним
  `BleMessageDecoder` зі штучним розбиттям; відхилень немає.
- Tracker отримує кадри та телеметрію за їхніми host timestamps;
  результат 27 / 20 / 17 / 0 підтверджено.
- JSON roundtrip зберігає всі поля та порядок кадрів; CSV зберігає порядок seq.
- Історичні captureMetadata та оригінальний файл не змінюються.

Це перевірка збережених JSON-об'єктів, не відтворення невідомих первісних
BLE-fragments і не фізичний тест. На цьому етапі код застосунку не змінювався;
оновлено звіт. Попередні 104 тести та збірки описані в розділі 5.

Артефакти в ігнорованому `build/validation/schema2_integrity/`:
`analysis.json` (усі індекси, переходи, повтори й телеметрія навколо них),
`replay_test.dart`, `replay_test.log`, `dart_replay.json`.
Для локального повтору: `flutter test --no-pub build/validation/schema2_integrity/replay_test.dart`.
Наступний фізичний тест має зіставити сирі FF11 bytes **до reassembly**
з тим самим потоком через USB; старих лічильників для локалізації причини недостатньо.
