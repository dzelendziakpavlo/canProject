# CAN Bus Diagnostics: реалізація та перевірка

Дата: 25.11.2026. Порти за повідомленням користувача: **SENDER — COM5,
RECEIVER — COM4**. Порти не відкривались, пристрої не перепрошивались.
Фізичний експеримент у межах цієї роботи не виконувався.

## Результат аудиту

Апаратний шлях «Connect to Stand» відкриває `MonitorScreen` із
`BleCanSource` або `SerialCanSource`. Окремий `ModernMonitorScreen`
використовує симулятор; його не слід використовувати для оцінювання стенду.

Обидва апаратні джерела вже мають незалежні `frameStream` та `statsStream`.
Таймер інтерфейсу працює кожні 50 мс, навіть коли немає кадрів. Попередня
реалізація перевіряла тишу лише у стані `streaming`, не мала спільної
перевірки свіжості BLE-телеметрії та залишала стару статистику після
втрати з'єднання. Накопичувальні RX-втрати могли постійно знижувати живий
HealthScore навіть після припинення нових втрат.

`CanFrame.isCorrupted` та `CanFrame.errors` описують конкретне повідомлення.
Припинення трафіку не змінює вже прийняті кадри на помилкові. Пошкоджені
на шині повідомлення можуть бути відхилені TWAI до `twai_receive()`;
їхнього CAN ID у статистичному пакеті немає.

У поточних файлах SENDER задано `SEND_MODE=1`, RECEIVER —
`CAN_TWAI_MODE=TWAI_MODE_NORMAL`, CAN 500 кбіт/с, USB RECEIVER 460800 бод,
Serial SENDER 115200 бод. Це конфігурація **вихідного коду**, а не перевірка
того, що зараз записано у флеш-пам'ять плат. Режими Extended/RTR не є
ознаками пошкодження повідомлення.

## Межа доступної апаратної інформації

Перевірено встановлені Arduino ESP32 Core 3.3.10 та ESP-IDF 5.5.4
(`versions.txt`: `735507283d`). RECEIVER використовує legacy
`driver/twai.h`, `twai_get_status_info()`, без типізованого `on_error`.

Публічна структура `twai_status_info_t` містить TEC/REC та загальний
`bus_error_count`, але не окремі CRC/Stuff/Form/ACK/Bit-лічильники.
Legacy-драйвер обробляє bus-error через загальний лічильник та alert.
Джерело: [ESP-IDF 5.5.4, legacy TWAI driver](https://github.com/espressif/esp-idf/blob/v5.5.4/components/driver/twai/twai.c).

Це обмеження поточного API, а не твердження про повну відсутність
можливостей у контролера. HAL уже читає ECC та розрізняє частину причин
у своєму приватному контексті. Читання ECC також переозброює Bus Error
Interrupt; незалежне читання з Arduino loop може втручатися в ISR драйвера.
Джерела: [HAL, обробка ECC](https://github.com/espressif/esp-idf/blob/v5.5.4/components/hal/twai_hal_v1.c#L262),
[LL, семантика читання ECC](https://github.com/espressif/esp-idf/blob/v5.5.4/components/hal/esp32/include/hal/twai_ll.h).

Безпечного публічного getter для такого типізованого запису в використаному
legacy API немає. Для його отримання потрібна окрема зміна драйвера або
міграція, з перевіркою синхронізації та втрат. Такої зміни не виконували.
Прошивки, BLE GATT/FF11/FF12, декодери, Android native bridge, USB Serial
та схема SQLite у цьому завданні не змінювалися.

## Панель та джерела показників

Панель **CAN Bus Diagnostics** розміщена над таблицею кадрів апаратного
монітора. На малих екранах вміст прокручується вертикально; метрики
переносяться на наступний рядок. Доступні останні три діагностичні події
та діалог із останніми 50 подіями.

| Показник | Джерело та інтерпретація |
|---|---|
| Traffic Active | Отримано кадр у межах останніх 3 с; host observation, inferred |
| Traffic Silent | Немає кадрів понад 3 с, але є свіжа статистика; inferred, причина Unknown |
| Traffic Unknown | Немає достатнього актуального спостереження або втрачено транспорт |
| Transport | Стани `CanFrameSource` та час останнього отриманого кадру/статистики |
| TWAI state | Поле `state` свіжого пакета статистики |
| TEC / REC | Поля `txe` / `rxe` контролера вузла, указаного в `node` |
| Bus errors | `buserr`, накопичувальний лічильник поточної епохи контролера |
| Δ bus errors | Різниця двох доступних послідовних знімків; перший знімок — Δ N/A |
| RX missed / overrun | `missed` / `ovr`; відсутнє поле — N/A |
| CRC / Stuff / Form / ACK / Bit | N/A: поточна схема не передає підтверджені лічильники цих типів |
| Node | Лише явно переданий `node`; без нього Unknown |
| Direction | Unknown: поточний пакет не містить напряму конкретної помилки |
| Час події | UTC приймання або спостереження на хості, джерело явно збережено |

`buserr=0` є виміряним нулем загального лічильника. Він не замінює
відсутніх типізованих полів нулями. Форматування типізованих метрик
розрізняє числове значення, включно з 0, та недоступне значення N/A;
поточний адаптер доказів повертає N/A для всіх п'яти категорій.
Поле `noack` є конфігурацією, а `sdemo` — прапорцем демонстраційного режиму;
вони не доводять ACK/Stuff/Form-подію. Загальний `txfail` також не доводить ACK.
Статистика RECEIVER не підміняє діагностику передавача SENDER.

RX missed може враховувати не лише чергу, а й втрати, пов'язані з
увімкненими workaround контролера. Arbitration lost саме по собі не є
CRC/Stuff/Form/ACK-помилкою. USB/BLE parse errors, пропуски sequence та
втрати транспортних черг залишаються транспортними показниками.

## Переходи, події та HealthScore

- Логіку розширено в наявному `TelemetryDiagnostics`; нового паралельного
  аналізатора не створено. Панель і HealthScore отримують одне поточне
  спостереження, перевірене на свіжість.
- Статистика актуальна протягом 4 с після отримання. Від'єднання,
  перепідключення та перезапуск скидають поточну базу. Зменшення лічильників
  або uptime починає нову епоху без віднімання через reset/rollover.
- Повтор ідентичного пакета з тим самим uptime підтверджує активність
  транспорту, але не продовжує актуальність статистики контролера.
- Silent записується один раз на початку; новий кадр завершує його подією
  відновлення. Втрата транспорту завершує спостереження як interrupted,
  **не** як підтверджене відновлення CAN.
- TEC/REC, стан та прирости лічильників породжують події з доказом
  `telemetry`, який UI позначає `hardware (telemetry)`. Час — час приймання
  знімка, а не точний час фізичної помилки. Інтервал знімків збережено.
  За незмінної несправності однакові події щосекунди не дублюються.
- Усі нові події використовують наявну `CanSessionEvent`, зберігають
  node, невідомий direction, severity, evidence і timestampSource.
  Недоступні прирости необов'язкових лічильників зберігаються як null.
- Події передаються в наявний `CanSessionService` і зберігаються разом із
  сесією. USB raw JSONL/CSV залишаються журналами wire-повідомлень; нові
  inferred-події не дописуються до них як нібито апаратні пакети.
  Наявні межі пам'яті збережено: UI 50 останніх діагностичних подій,
  live session до 2000 подій для USB/SQLite-backed захоплення; BLE writer
  записує прийняті події до SQLite незалежно від цього live-обмеження.
- Використовується `CanHealthAnalyzer`: Silent −25, error passive −20,
  warning −10, bus-off −40, recovering −25, поточні нові RX-втрати −15.
  Після припинення відповідного стану його штраф зникає; накопичувальний
  лічильник не обнуляється. Інші наявні правила оцінювання збережено.
  Сам загальний buserr не перетворюється на вигаданий тип помилки.
- Якщо свіжої статистики немає, апаратний HealthScore у картці — N/A.
  Історична аналітика збереженої сесії описує весь запис, а не лише
  актуальний стан, і може продовжувати показувати минулі аномалії.

## Перевірка на стенді

1. Запусти оновлену Windows-збірку
   `build\windows\x64\runner\Release\can_debug.exe`. Закрий програми,
   що займають RECEIVER COM4. Через Connect to Stand → USB Serial вибери
   **COM4, 460800**, якщо поточна прошивка відповідає цим налаштуванням.
   Для Android установи `build\app\outputs\flutter-apk\app-debug.apk`
   та підключись до CAN-Monitor через BLE і Connect to Stand.
2. Залиши штатний обмін CAN. Очікується Traffic Active, Transport Active,
   фактичні TEC/REC/state та N/A для непереданих типів помилок. На COM5
   можна окремо спостерігати текстову статистику SENDER на 115200 бод;
   її показники не надходять автоматично до панелі RECEIVER.
3. Припини передавання SENDER, залишивши RECEIVER і його USB/BLE
   увімкненими. Якщо статистика продовжує надходити, через понад 3 с
   з'являться Traffic Silent і `CAN traffic lost — no frames received`.
   У чистому сценарії HealthScore зміниться 100 → 75. Старі кадри
   збережуть свої попередні статуси.
4. Віднови передавання. Наступний кадр має повернути Active; у журналі
   має бути одна подія відновлення. У чистому сценарії оцінка повернеться
   до 100. GPIO5 можна перевірити аналогічно до твого попереднього
   експерименту, проте конкретна реакція лічильників не гарантується:
   панель показує отриману статистику, а не приписує обриву тип ACK/CRC.
5. Окремо від'єднай USB RECEIVER або розірви BLE. Очікується Transport
   Disconnected/Connecting і Traffic Unknown. Якщо з'єднання формально
   лишилося, але даних немає понад 4 с, буде Stale. Старі TEC/REC не
   повинні лишатися актуальними. Перепідключися: до свіжого знімка
   метрики недоступні, попередня тиша не стає фальшивим recovery.
6. Заверши через Disconnect & Save. Відкрий збережену сесію/її JSON
   і перевір події з `component=can_bus_diagnostics`, фазами
   started/recovered/interrupted, evidence і timestampSource.

Зміна bitrate не є способом гарантовано створити кадр із червоною рамкою
або окремий CRC/ACK-лічильник. Фізичні результати цих кроків ще потрібно
перевірити на стенді; програмні тести їх не підміняють.
