# CAN Debug Pro — фінальні результати дослідження BLE для підрозділу 4.2

Дата фіналізації: 2026-11-10. **Дослідження цілісності BLE завершене в погодженому обсязі.** Цей документ фіксує результати; продовження трасування Bluetooth-стека, нові BLE-тести та патчі не плануються.

## 1. Мета, конфігурація та межі висновків

Мета — перевірити одночасне передавання прийнятих CAN-кадрів і телеметрії через Windows USB Serial та Android BLE, відокремити пошкодження повідомлень від втрат журналювання й локалізувати інтервал появи розбіжності. Перевірка не є вимірюванням бітових помилок CAN або радіоканалу Bluetooth.

Стенд: два ESP32 із SN65HVD230; SENDER генерує Classical CAN, RECEIVER приймає його через TWAI. CAN 500 kbit/s; SENDER `SEND_MODE=1`: вісім стандартних ID, сумарно близько **36 кадрів/с**, а не 80. У data змінюються перші два байти, `data[1]=(data[0]*3)&255`. RECEIVER присвоює `seq` після успішного `twai_receive()` та копіює одну серіалізацію кадру в окремі BLE/USB-черги. USB: 460800 бод, 8N1, без flow control; порт у наведених контрольних записах COM5. BLE: FF10 service, FF11 frames, FF12 stats приблизно раз на секунду. USB stats додатково містять transport counters.

Android native trace: Android SDK 30, legacy notification callback; `flutter_blue_plus 1.36.8` / локально закріплений `flutter_blue_plus_android 7.0.4` із незалежним snapshot. MethodChannel отримує саме копію. Дисковий журнал асинхронний, RAM-черга 1024 записи, dropped/write/pending counters явні. Він незалежний від SQLite та UI-буфера на 100 кадрів.

Діагностичні збірки RECEIVER ідентифіковані headers/build manifests: Arduino-ESP32/BLE 3.3.10, ESP-IDF 5.5.4, commit `735507283d`, Bluedroid. Для початкових записів до діагностичних headers версію прошитого binary не можна ретроспективно засвідчити лише за поточним скетчем чи рядком `fw=can-monitor-telemetry-v2`. У первісному logcat узгоджений MTU 247; це не автоматична атестація MTU всіх наступних запусків.

Надані в контексті назви T01–T05 не прив'язані у знайдених звітах до однозначного реєстру запусків. Нижче використано власні позначення **B0–B5**, що однозначно посилаються на файли; вони не замінюють нумерацію T01–T05. Не відновлюємо відсутні результати T01–T05 припущеннями. Окремі USB manifests 115200/921600 та overload не є парними доказами цілісності BLE й не використовуються для загального твердження «USB завжди без втрат» або про оптимальний baud.

## 4. Конкретні аномалії

### Змішування FF11 і FF12 — B1 callback №3035

Characteristic у native записі — **FF12**, довжина 225 байтів. Повний вміст точно розкладається так:

```text
observed_FF12 = USB_FF11(seq=8033)[0:78]
              + USB_base_FF12(uptime=220570, rx=7890)[78:225]
```

Перші 78 байтів утворюють повний JSON кадру ID 192, data `[234,190,0,0,0,0,0,0]`, ts=224541, seq=8033; далі залишається 147-байтовий хвіст старішого stats JSON. Це один native callback, а не результат конкатенації у Dart. Його snapshot length/hash узгоджені, `original_matches_snapshot=true`. Побайтове накладання доведене; місце й механізм його виникнення цим прикладом не встановлені. Докладні дані — [ESP32_RECEIVER_BLE_AUDIT.md](ESP32_RECEIVER_BLE_AUDIT.md).

### B3: ESP32 №193 → native №197

На dequeue, після setValue і на вході send API: 75 байтів, ID 200, data `[188,52,0,0,0,0,0,0]`, ts=18137, `seq=604`, JSON закінчується `"seq":604}`. Native має ті самі 75 байтів за довжиною, але кінець `"seq":6001`, без закривальної дужки. Це malformed callback; постійність довжини не означає цілісність вмісту.

### B4: ESP32 №27 і №44 → native №39 і №56

Для №27 правильний seq=6406, data `[27,81,0,0,0,0,0,0]`, ts=179270; після реального deep-copy байти правильні. Native №39 має data `[6,18,0,0,0,0,0,0]`, ts=179171, seq=6403 та зайву `}`. Для №44 правильний seq=6422, ID 424, data `[7,21,0,0,0,0,0,0]`, ts=179671; native №56 має data `[16,48,0,0,0,0,0,0]`, seq=6420 і не має кінцевої `}`. Post-deep-copy snapshots в обох випадках збігаються з USB; обидва пошкоджені native JSON невалідні.

### B5: ESP32 №19, token=19 → native №23

На всіх виміряних ESP32 етапах, **включно з входом `btc_gatts_call_handler()`**:

```json
{"t":"f","id":208,"dlc":8,"data":[101,47,0,0,0,0,0,0],"ts":123382,"seq":4395}
```

У native callback №23:

```json
{"t":"f","id":208,"dlc":8,"data":[101,47,0,0,0,0,0,0],"ts":123382,"seq":4393}
```

Обидва мають 77 байтів; змінена остання цифра seq. Правильний seq=4393 вже надійшов у callback №21 з ID 192. Для №19 API/copy token=19, `copyMessageAddress=1073737552`; handler має той самий token і message address, payload pointer=1073737604, handle=42, length=copied=77, flags=0. Fingerprint dequeue/set/API/source-copy/post-copy/handler — `7b676e5457d4e58b657f5fa87b9244c0` (перші 128 біт SHA-256). На пристрої також виконано повне порівняння байтів; звичайні RAM records зберігають довжини та fingerprints, а не всі повні payload. Наведений правильний текст — точний USB payload, що відповідає цим відбиткам.

## 5. Що перевірено та що доведено

| Компонент / межа | Доказ і допустимий висновок |
|---|---|
| Windows USB журнал | У B0–B4 послідовні кадри та узгоджені manifests у конкретних записах. У B5 є окремий rejected record; загальний безпомилковий USB висновок для нього неприйнятний. |
| Dart decoder, mapper, sequence tracker, SQLite, UI, export | Суперечливі bytes уже видно до цих компонентів. Вони не можуть бути джерелом саме цих раніше зафіксованих аномалій; загальна бездефектність компонентів цим не доведена. Replay B0 відтворив вхід без зміни bytes. |
| Android callback → відкладений MethodChannel | Snapshot створено на вході callback; журнал повний, originalMutationCount=0 у B1/B2 і контрольних трасованих запусках. Мутації оригіналу за час відкладання в цих записах не виявлено; snapshot patch сам проблему не усунув. |
| ESP32 dequeue → characteristic readback → send API | У B3–B5 виміряні lengths/fingerprints узгоджені, on-device comparison не виявив змін. FF11/FF12 peer characteristic не змінилася під час setValue/readback; між виміряними повідомленнями continuity differences немає. |
| Реальний BTC deep-copy | B4/B5: власний destination snapshot після оригінального callback копіювання; tokens/metadata/байти узгоджені, alias не зафіксований. Зміни саме під час цього копіювання не виявлено. |
| Post-deep-copy → вхід BTC handler | B5: усі 128 tokens зіставлені, payload і metadata незмінні, full-fault records не виникли. Зміни на цій межі у виміряній когорті не виявлено. |

Статичний аудит також перевірив черги зі зберіганням за значенням, локальні String/WireMessage та один активний BLE writer. В установленій версії setValue копіює payload; send API викликає deep-copy до постановки BTC message в чергу. Це узгоджено з результатами вимірювань, але не поширюється на будь-які версії стеків чи неідентифіковані прошивки.

**Остання підтверджена точка цілісності для локалізованої аномалії B5 — незалежний snapshot на вході `btc_gatts_call_handler()` перед викликом оригінального handler. Перша точка спостереження зміненого вмісту — незалежний snapshot на вході Android native notification callback.** Інтервал між цими точками не розділено подальшими вимірюваннями; несправність не локалізована до конкретної його функції, пристрою чи радіопакета.

## 6. Непідтверджені гіпотези та невідомі обставини

Не підтвердилися як пояснення виміряних випадків: зміна JSON у Dart/SQLite/export; мутація оригінального Android byte array між entry та UI runnable; пошкодження на setValue/readback або вході send API; зміна під час BTC deep-copy; зміна між post-copy та handler entry. Нуль змін у короткій когорті не є універсальним доказом відсутності будь-якого race в усіх режимах.

Не доведені: buffer reuse як механізм, BTC queue як винуватець, дефект ESP-IDF, пошкодження у radio, помилка конкретного Android GATT компонента. FF12 overlay показує форму змішаного вмісту, але не визначає його автора. Не встановлені точний момент і механізм зміни після handler entry, over-the-air bytes, загальна імовірність пошкодження, гарантована частка BLE-втрат або end-to-end latency. Окремо невідоме походження rejected USB record B5.

## 7. Технічний висновок для 4.2

Паралельне приймання USB Serial/BLE реалізоване й спостерігалось у парних записах. USB є придатним контрольним джерелом для наведених узгоджених capture-вікон; безумовної гарантії нульових втрат на будь-якому навантаженні немає. BLE може доставляти як malformed JSON, так і структурно валідні, але суперечливі повідомлення. Parser validation і перевірка seq дають додаткові ознаки, проте не гарантують правильності всіх полів кадру. Під час дослідження аномалії локалізовано після входу BTC handler і до входу Android native callback для конкретного виміряного повідомлення. Першопричина не встановлена; функціональне усунення дефекту не підтверджене. Для CAN-експериментів 4.3 контрольним каналом обрано USB, результати BLE не використовуються як єдине джерело апаратних лічильників.

## 8. Академічний текст українською для адаптації

Для оцінювання достовірності діагностичних даних виконано порівняння двох каналів передавання від ESP32 RECEIVER: USB Serial до Windows та BLE до Android. Зіставлення здійснювали за полями повідомлень, послідовними номерами та незалежними знімками байтів. У контрольних USB-записах B0–B4 не виявлено пропусків послідовних номерів і помилок розбору, тоді як у BLE зафіксовано як невалідні JSON-повідомлення, так і валідні об'єкти з полями, що суперечать відповідним USB-даним. Показники окремих запусків розглядали окремо через різні тривалість і межі запису.

Додаткове трасування дозволило відокремити ці порушення від оброблення у Flutter, збереження в базі даних та експорту. В одному з контрольних запусків для 128 повідомлень підтверджено незмінність вмісту від вихідної BLE-черги до входу обробника BTC, включно з копіюванням payload у власну пам'ять Bluetooth-стека. Водночас для одного повідомлення на вході Android native callback зафіксовано зміну seq з 4395 на 4393 за незмінної довжини та решти полів. Таким чином, для цього випадку визначено інтервал появи розбіжності між двома точками спостереження, проте не встановлено її конкретну програмну або апаратну причину.

Отримані результати обґрунтовують окреме врахування достовірності транспортних даних під час діагностики CAN. Ознаки порушення цілісності BLE-повідомлень не слід інтерпретувати як апаратні помилки CAN, а відсутність номера в журналі — автоматично як втрату радіопакета. Подальші експерименти з реакцією CAN-стенду доцільно виконувати з USB Serial як контрольним каналом, із збереженням первинних повідомлень, лічильників втрат та меж застосовності висновків. Дослідження внутрішньої причини BLE-порушень у межах цього етапу завершено без твердження про усунення дефекту.
